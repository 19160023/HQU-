# 校园活动汇 — 校园活动聚合与时间轴系统

桑梓实验室 2026 纳新项目任务书 · **基础要求六项已验收通过，并完成了「数据与工程」方向的加分项**。

一个把学院、学生组织、个人发布的活动集中起来的网页系统：按时间看活动、看详情、发布、搜索、留言。后端提供 JSON 接口，数据存在 SQLite 数据库里，带账号与权限。

> 页面里所有示例活动都是**虚构的**，不包含任何真实同学的信息。

---

## 项目目标

学院、学生组织、个人都在发活动，信息散在公众号、QQ 群、微信群里。想知道"这个活动哪天开始、哪天截止报名、要注意什么"，往往要翻好几个地方。

这个项目把那三类发布者的活动聚到一处：

- **同学**：一进来就能按状态看到"还能报名的""正在办的""已经结束的"，能按时间看跨度，能搜、能筛、能点进详情看介绍和参与方式，能在活动下面留言补充报名经验。
- **发布者**：登录后直接发布，表单会拦住时间写反、截止晚于结束这类错误。
- **管理员**：能下架不实或过期的活动；下架的活动对普通同学完全不可见。

不做的事：不接学校真实系统、不做统一身份认证、不采集任何真实同学的个人信息与报名名单。

## 一、怎么跑起来

需要 **Node.js 22.5 或更高版本**（用到了 Node 内置的 `node:sqlite`，不需要 `npm install`，没有任何第三方依赖）。

```bash
# 方式一：双击 启动.bat
# 方式二：命令行
node server/server.mjs 8080
```

浏览器打开 <http://localhost:8080>

**进场是一条完整动线**：

```
打开 http://localhost:8080
   ↓  封面页（品牌 + 一句介绍，0.5 秒后「进入校园活动汇」按钮浮现）
点「进入」或按回车
   ↓  登录 / 注册页
   ├─ 登录或注册成功  →  活动列表
   └─ 点「先不登录，直接浏览活动」→ 活动列表（游客只能看和留言）
```

- 根路径 `/` 是封面页，活动列表在 `/index.html`。站内导航都直接指向 `index.html`，所以翻页不会再弹封面。
- 已经登录过的人再点「进入」，会跳过登录页直接进列表（按钮下面的小字会提示「已登录，直接进入活动列表」）。
- 保留游客入口是任务书 二.1「所有同学都可以浏览这些活动」的要求，不能被登录墙挡住。

首次启动会自动建库、建表、灌入 17 条示例活动和 6 条示例留言，并在控制台打印演示账号：

| 账号 | 密码 | 身份 | 能做什么 |
|---|---|---|---|
| `admin` | `admin2026` | 管理员 | 下架/恢复任何活动、恢复示例数据 |
| `college01` | `college2026` | 学院 | 以学院身份发布活动 |
| `org01` | `org2026` | 学生组织 | 以学生组织身份发布 |
| `student01` | `student2026` | 个人 | 以个人身份发布 |

> 这些是本地演示用的固定密码，别在真实环境里这么干（README 末尾的已知问题里写了）。

数据库文件在 `data/campus-events.db`，想清空重来：删掉 `data/` 目录再启动。

## 二、六个基础要求怎么对应到实现

| 任务书要求 | 实现 | 页面 |
|---|---|---|
| 二.1 活动浏览与详情 | 卡片显示名称/类型/发布者/起止时间/报名截止；三类发布者用颜色和标签区分；**列表按状态分块（报名中 / 进行中 / 报名已截止 / 已结束 / 已下架）**；详情含介绍与参与方式 | `index.html`、`detail.html` |
| 二.2 时间轴 | 甘特式时间条：条长=持续天数，▼=报名截止，两者从不合并；顶部日期刻度与条共用同一套坐标 | `index.html?view=timeline` |
| 二.3 活动发布 | 9 个字段 + 6 条校验；发布者身份由登录账号带入 | `publish.html` |
| 二.4 搜索与筛选 | 关键词（标题/介绍/发布者）+ 类型 + 面向对象，三条件叠加，在列表和时间轴同时生效 | `index.html` |
| 二.5 评论 | 详情页留言区，昵称（可留空）+ 内容（必填）+ 时间，倒序 | `detail.html` |
| 二.6 数据保存与可用性 | 数据存数据库、操作有明确提示、导航打通、手机宽度可用 | 全站 |

## 三、「数据与工程」加分项做了什么

任务书该方向列了四件事，逐条对上：

| 文档要求 | 本项目的实现 |
|---|---|
| 用数据库保存数据 | SQLite（`node:sqlite`），4 张表 + 5 个索引 + CHECK 约束，见 `docs/数据模型.md` |
| 前后端分离，由后端提供接口 | 页面只通过 `fetch` 调 `/api/*`，共 15 个接口，见 `docs/接口说明.md` |
| 设计数据模型并附表结构说明 | `server/schema.sql` + `docs/数据模型.md`（含字段表、索引表、4 条设计取舍） |
| 实现账号与基础权限 | 注册/登录/退出、scrypt 密码、HttpOnly Cookie 会话、三种角色权限（见下表） |

### 权限模型

| 角色 | 浏览 | 留言 | 发布 | 删自己的 | 删别人的 | 下架活动 | 恢复示例数据 |
|---|---|---|---|---|---|---|---|
| 游客 | ✅ | ✅ | ❌ 提示登录 | ❌ | ❌ | ❌ | ❌ |
| 普通用户 | ✅ | ✅ | ✅ | ✅ | ❌ 403 | ❌ 403 | ❌ 403 |
| 管理员 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

三条关键约束，都在后端强制：

1. **发布者身份不能被前端伪造**：请求里的 `publisherType` / `publisherName` 一律忽略，服务端取登录账号上的值。
2. **删除只能删自己的**：`created_by` 与当前用户比对，管理员例外。
3. **下架后普通用户看都看不到**：列表过滤 + 详情返回 404，而不是只在前端藏起来。

## 四、架构

```
浏览器
  index.html / detail.html / publish.html / login.html
  js/ui-*.js ──► js/api.js ──fetch──┐
  js/templates.js  js/timeline.js   │
  js/core.js  js/validation.js（纯函数，前后端共用）
                                    │
                             server/server.mjs   ← 静态文件 + /api 路由
                                    │
                          server/api.mjs（路由与权限）
                                    │
                    server/db.mjs + schema.sql（SQLite）
```

两处值得说的：

**纯函数前后端共用。** `js/core.js`（状态判定、日期换算）、`js/validation.js`（表单校验）、`js/timeline.js`（时间轴坐标）都不碰 DOM，浏览器里跑，Node 里也跑。所以：
- 前端提交前用同一套规则先校验一次，用户立刻看到红字；
- 后端收到请求再用同一套规则校验一次，并按同一套规则算时间轴坐标——不存在"前端算一套、后端存一套"的漂移。

**静态资源和接口同进程。** 本机演示时省掉跨端口 CORS 和 Cookie 的配置。接口本身是标准 JSON API，可以用 curl 单独调用（`docs/接口说明.md` 最后一节有例子）。

## 六、测试

```bash
node tests/smoke.mjs      # 数据、日期、状态分组、封面去向 38 项
node tests/render.mjs     # 页面模板渲染               47 项
node tests/timeline.mjs   # 时间轴坐标                 34 项
node tests/publish.mjs    # 发布表单结构与校验         53 项
node tests/comments.mjs   # 留言校验与渲染             35 项
node tests/api.mjs        # 后端接口与权限（真起服务） 64 项
node tests/dom.mjs        # 页面脚本在"浏览器替身"里跑 43 项
```

合计 **314 项断言，全部通过**。

`tests/api.mjs` 不是 mock：它用 `:memory:` 数据库真起一个 HTTP 服务，再用 `fetch` 当客户端打接口，覆盖注册登录、重复注册、密码错误、无权限发布、越权删除、管理员下架、下架后 404、LIKE 通配符转义等。

`tests/dom.mjs` 也真起了服务，额外用一个最小 DOM 替身把 `ui-list.js`、`ui-detail.js`、`ui-publish.js` 原样跑一遍，验证"首屏渲染出 17 张卡片、事件确实绑上了、点类型能筛、搜索能筛、详情页能显示留言、发布页按账号渲染身份"。它专门用来抓"脚本跑到一半抛错导致整页没反应"这类纯 Node 测试看不到的问题。

## 七、已知问题

- **没有做编辑活动**。接口留了位置但没实现 PATCH，前端也没有编辑入口。要加的话是"详情页进编辑态 + PATCH 接口"两块。
- **审核只有"下架/恢复"两态**，没有"待审核队列"。个人上传的活动直接可见，管理员事后下架。
- **演示账号是固定密码**，正式部署必须改掉或删除；`SESSION_DAYS`、Cookie 也没配 `Secure`（本地是 http）。
- **没有 CSRF token**。目前靠 `SameSite=Lax` + 只接受 JSON 请求体挡着，生产环境还应加 token。
- 没有分页，一次最多返回 500 条活动。
- 手机端只是"能用"，没有针对触摸优化（时间轴要横向滑）。
- 日期粒度是"天"，没有时分。

## 八、AI 与开源资料使用情况

按任务书要求如实说明：

**用了什么工具。** 整个项目在 **AI 编程助手（DeepSeek）** 的辅助下完成，属于"人机协作"而不是"复制一个现成项目"。

**分工大致是这样：**

| 环节 | 谁做的 |
|---|---|
| 需求拆解、页面与时间轴方案、技术选型 | 人定方向，AI 出草案；方案在 `docs/计划与验收.md` 里逐条确认过 |
| 代码编写 | 主要由 AI 生成，人逐模块验收、提修改意见 |
| 测试设计 | 人与 AI 共同设计；7 个测试文件、314 项断言由人逐条看过结论 |
| 问题排查 | 人发现现象（如列表页白屏），AI 定位根因（`let` 暂时性死区）并修复，排查过程记录在 `docs/验收记录.md` |
| 验收 | 每个功能由人逐条点击验收后才进入下一个（见 `docs/验收记录.md`） |

**能讲到什么程度。** 时间轴坐标算法、三条时间校验规则、权限判定这三处，是可以逐行讲清设计意图和实现细节的；其余部分（模板拼接、样式）能说明思路。

**开源资料。** **没有引入任何第三方库、框架或开源代码。** 具体说：

| 用到的东西 | 来源 |
|---|---|
| SQLite 数据库 | Node.js 内置模块 `node:sqlite` |
| 密码哈希（scrypt）、随机数 | Node.js 内置模块 `node:crypto` |
| HTTP 服务、静态文件 | Node.js 内置模块 `node:http` / `node:fs` |
| 前端框架 | 无，原生 JS（ES Module） |
| CSS 框架 | 无，手写样式，无外部字体与图标库 |

**数据。** 17 条示例活动、6 条示例留言全部是编的，人物姓名、学院、联系方式均为虚构；未使用任何未公开的学院或组织内部材料。
