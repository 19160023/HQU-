# 数据模型与表结构说明

数据库：**SQLite**（Node 24 内置 `node:sqlite`，不需要安装任何依赖，也不需要单独起数据库服务）
建表语句：`server/schema.sql`　初始化数据：`server/db.mjs`　数据库文件：`data/campus-events.db`

---

## 一、四张表的关系

```
users ──1:N──> activities ──1:N──> comments
  │                 │                  │
  └──1:N──> sessions└── created_by     └── created_by
                       （谁发的）           （登录用户留的言，游客为 NULL）
```

- 一个用户可以发多个活动、留多条言。
- 活动删除时，它下面的留言**级联删除**（`ON DELETE CASCADE`）。
- 用户被删除时，他发过的活动和留言保留，`created_by` 置空（`ON DELETE SET NULL`）——不因为删账号而丢内容。

## 二、表结构

### 1. `users` 用户

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | INTEGER | 主键自增 | |
| account | TEXT | 唯一、非空 | 登录名，4–20 位字母数字下划线 |
| display_name | TEXT | 非空 | 显示名，页头和留言默认昵称用它 |
| password_hash | TEXT | 非空 | scrypt 派生值（十六进制，64 字节） |
| salt | TEXT | 非空 | 每个用户独立随机盐 |
| role | TEXT | `user` / `admin` | 权限角色，CHECK 约束 |
| publisher_type | TEXT | `college`/`org`/`personal` | 发布者身份，注册时选，之后不可在发布表单里改 |
| publisher_name | TEXT | 非空 | 发布活动时默认填的发布者名称 |
| created_at | TEXT | 非空 | ISO 时间串 |

> 密码不存明文。用 `scryptSync(password, salt, 64)` 派生，比对时用 `timingSafeEqual` 定长比较，避免按响应时间猜密码。

### 2. `sessions` 会话

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| token | TEXT | 主键 | 32 字节随机数的十六进制 |
| user_id | INTEGER | 外键 → users.id，级联删除 | |
| created_at | TEXT | 非空 | |
| expires_at | TEXT | 非空 | 7 天过期，过期即视为未登录并删掉该行 |

> token 只存在 **HttpOnly Cookie** 里，前端 JS 读不到，降低 XSS 拿到会话的风险。

### 3. `activities` 活动

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | TEXT | 主键 | `a_` + 随机串；示例数据用 `a01`–`a17` |
| title | TEXT | 非空 | 活动名称 |
| category | TEXT | 非空 | 六种类型之一（接口层再校验一次） |
| publisher_type | TEXT | CHECK 三选一 | 学院 / 学生组织 / 个人 |
| publisher_name | TEXT | 非空 | 发布者名称 |
| audience | TEXT | 非空 | `全校` 或具体学院 / 年级 |
| start_date | TEXT | 非空 | `YYYY-MM-DD` |
| end_date | TEXT | 非空 | `YYYY-MM-DD`，**CHECK: ≥ start_date** |
| signup_deadline | TEXT | 非空 | `YYYY-MM-DD`，**CHECK: ≤ end_date** |
| description | TEXT | 非空 | 活动介绍，空行分段 |
| link | TEXT | 默认 '' | 参与方式 / 链接 |
| is_sample | INTEGER | 0/1 | 是否示例数据 |
| hidden | INTEGER | 0/1 | 管理员下架标记，下架后普通用户列表和详情都看不到 |
| created_by | INTEGER | 外键 → users.id，SET NULL | 发布者账号，示例数据为 NULL |
| created_at | TEXT | 非空 | |
| updated_at | TEXT | 非空 | 下架/恢复时更新 |

索引：

| 索引 | 用途 |
|---|---|
| `idx_activities_start` | 时间轴、按开始时间排序 |
| `idx_activities_category` | 类型筛选 |
| `idx_activities_audience` | 面向对象筛选 |
| `idx_activities_hidden` | 过滤已下架 |

> **两条时间规则同时写在数据库 CHECK 里**：接口层用 JS 校验是为了给用户一句人话，数据库 CHECK 是最后一道保险——万一哪天有新代码绕过接口直接写库，脏数据也进不去。

### 4. `comments` 留言

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | TEXT | 主键 | `c_` + 随机串 |
| activity_id | TEXT | 外键 → activities.id，**级联删除** | |
| nickname | TEXT | 非空 | 昵称，留空由接口补「匿名同学」 |
| content | TEXT | 非空 | 留言内容，≤ 500 字 |
| created_by | INTEGER | 外键 → users.id，SET NULL | 登录用户留的言记账号；游客为 NULL |
| created_at | TEXT | 非空 | 列表按它倒序 |

索引：`idx_comments_activity(activity_id, created_at DESC)` —— 详情页按活动取留言并倒序，正好走这个索引。

## 三、几个设计取舍

**为什么 id 用 TEXT 而不是自增整数？**
前端链接是 `detail.html?id=a01`，一直用字符串 id。换成自增整数会让「示例数据 id 稳定」和「前后端 id 格式统一」两件事都变麻烦。TEXT 主键在几千条量级没有性能问题。

**为什么日期存 `YYYY-MM-DD` 字符串？**
同一天的比较、排序在 SQLite 里字符串比较就是字典序，等价于时间序，不需要额外的日期类型或时区换算。项目里所有日期都是"天"粒度（与前端一致）。

**为什么单独建 sessions 表，不全用 JWT？**
JWT 无法在服务端立刻失效（除非维护黑名单）。独立会话表能做到"退出登录即失效"、"管理员可以踢掉某个会话"、"7 天过期自动清理"，对课程作业来说也更直观。

**为什么把 `hidden` 放活动表，不单建审核表？**
当前只需要"下架/恢复"两种状态，一个 0/1 字段够用。如果以后要做"待审核 → 通过/驳回"的多步流程，再拆出 `reviews` 表更合适（这一点写在 README 的已知问题里）。

**示例数据与用户数据的区分**
`is_sample = 1` 表示这条是示例数据，管理员点「恢复示例数据」时会把全部活动删掉重灌；`created_by` 为空也说明它没有真实作者，任何人都不能删它（只有管理员能下架）。
